RoboForge SDK

A small Python library in which the simulator, the renderer, ROS 2 and MAVLink are interchangeable parts. You write the controller; the same code runs against MuJoCo, behind ROS topics, as a MAVLink vehicle, or on a real robot.

What it is

Most robotics stacks are glued together pairwise: a MuJoCo-to-ROS bridge, a PX4-to-Gazebo bridge, a MAVLink-to-ROS bridge. Each new combination needs new glue. Here every part publishes and subscribes named signals on one in-process bus (state/pose, sensor/imu, cmd/actuators…), so a new simulator or transport is one adapter and every combination already works.

import roboforge as rf

app = rf.App(robot="quadrotor",                                    # bundled model
             controllers=[rf.MultirotorController(rate=250)],      # setpoint -> motors
             links=[rf.MavlinkLink(mode="vehicle"), rf.Ros2Link()])  # be a MAVLink vehicle, mirror on ROS 2
app.run()

It is a library first: every part works on its own, app.step() lets you write the loop yourself, and physics.raw, link.raw hand you MuJoCo's, rclpy's and pymavlink's own objects whenever the abstraction is not enough.

Start a project

From the IDE

  1. New, then tick Build on the RoboForge SDK. Pick a quick combination (MuJoCo + ROS 2, MuJoCo + MAVLink, ROS 2 + MAVLink, All three) or set Simulator, Robot and Autopilot link yourself. ROS 2 is on when a ROS 2 distro is selected. Combinations that cannot work are refused with the reason.
  2. Create project. You get app/app.yaml, a starter app/controller.py (or app/mission.py for a MAVLink vehicle), run configurations, and a launch configuration.
  3. The Stack view opens. If it says a package is missing, press Set up SDK environment (see Python environment), then open Stack again.
  4. ▶ Run. For a MAVLink vehicle the launch configuration starts the app and then the mission script.

Tutorials

Seven small examples, one per idea. Each is a toy: CPU only, no GPU, about 150 MB of memory, and a few seconds to a minute to run. They were all run on a desktop with 8 cores, 31 GB of memory and a GTX 1070, where the simulator steps about eight times faster than real time; a laptop is enough.

The files ship with the IDE in ~/.roboforge/sdk/python/examples/ (and live in the repository under sdk/python/examples/). Copy a folder before editing it, or open it in the IDE with Open: the scanner recognises app.yaml and offers it in the Run menu.

Run the commands in a RoboForge terminal (Ctrl+`) of any SDK project, where python3 already has the SDK, MuJoCo and pymavlink. Outside the IDE, use the SDK environment's Python: ~/.roboforge/envs/sdk-venv/bin/python, after source /opt/ros/jazzy/setup.bash for the ROS tutorials. Add --headless to skip the viewer window; every tutorial works without it.

1. An arm on ROS 2 topics

A three-joint arm in MuJoCo. Your controller (controller.py, 50 Hz) emits joint targets; the built-in joint controller (500 Hz) turns them into torques; the ROS 2 link mirrors everything on topics.

cd mujoco_ros_arm
python3 -m roboforge info app.yaml             # the parts and who produces each signal
python3 -m roboforge run app.yaml --headless   # Ctrl+C to stop

In a second terminal:

ros2 topic hz /clock                           # average rate: 500
ros2 topic echo --once /joint_states           # three positions that change as the arm waves

Try next: change the amplitudes in controller.py and run again. Then delete the controller:Wave line from app.yaml and command the arm from ROS instead:

ros2 topic pub -r 10 /joint_command sensor_msgs/msg/JointState "{position: [0.5, 0.2, -1.0]}"

2. A wheeled base and cmd_vel

A differential-drive base. controller.py drives it in a circle; the built-in diff-drive controller converts forward speed and turn rate into wheel speeds.

cd diffdrive_ros
python3 -m roboforge run app.yaml --headless
ros2 topic echo --once /odom                   # position moves along a circle

Try next: remove the controller:Circle line from app.yaml and drive it yourself. Five seconds at 0.2 m/s moves it about one metre:

ros2 topic pub -r 10 -t 50 /cmd_vel geometry_msgs/msg/Twist "{linear: {x: 0.2}}"
ros2 run teleop_twist_keyboard teleop_twist_keyboard     # or the keyboard

3. A quadrotor flown over MAVLink

The app is the vehicle: it answers MAVLink the way an autopilot does, with no PX4 installed. mission.py is an ordinary MAVLink client.

cd mujoco_mavlink_quad
python3 -m roboforge run app.yaml --headless   # terminal 1
python3 mission.py                             # terminal 2

The mission prints, in about 15 seconds:

Try next: change the corners in mission.py; uncomment the recorder line in app.yaml to save the flight (tutorial 7 shows what to do with it).

4. All three: MuJoCo, MAVLink and ROS 2

The same flight as tutorial 3 with one more line in app.yaml: a ROS 2 link. Nothing else changes, which is the point of the signal bus.

cd mujoco_ros_mavlink_quad
python3 -m roboforge run app.yaml --headless   # terminal 1
python3 mission.py                             # terminal 2
ros2 topic echo /odom --field pose.pose.position          # terminal 3: watch it fly the square

ros2 topic list shows /clock, /odom, /imu, /tf and /camera/front/image_raw while MAVLink carries the commands.

5. ROS 2 and MAVLink with no simulator

A bridge for a real or separately simulated autopilot: MAVLink telemetry becomes /odom and /tf, and poses published on /setpoint_pose become MAVLink position targets. With no autopilot at hand, the vehicle from tutorial 3 stands in for one.

(cd mujoco_mavlink_quad && python3 -m roboforge run app.yaml --headless)   # terminal 1: the stand-in autopilot
(cd ros_mavlink_bridge && python3 -m roboforge run app.yaml)               # terminal 2: the bridge
ros2 topic echo --once /odom                                                 # terminal 3: the vehicle's pose, via MAVLink

Try next: point the url in ros_mavlink_bridge/app.yaml at a PX4 SITL or a telemetry radio.

6. From a PID loop to a slow policy

Three controllers share the arm, each at its own rate: a stand-in for a large model (2 Hz, 300 ms per inference, returning a chunk of future targets), rf.Async (50 Hz) that runs it off the loop and plays the chunk out, and the PID loop (500 Hz) that drives the motors. No model download and no GPU: the "model" is a time.sleep.

python3 pid_to_policy.py 20 --headless
roboforge: t=19.7s  x0.98 real time  async(SlowPolicy) 50 Hz  JointPD 500 Hz
policy: 62 inferences, 300 ms each, 16 late steps; PID loop ran at 500 Hz throughout

The late steps are the fallback holding a safe pose while the first inference is still running. Try next: raise the sleep in SlowPolicy past the chunk length and watch the late count grow while the PID rate stays at 500 Hz. Replace SlowPolicy with a real model and nothing else changes.

7. Record a flight and export a dataset

Flies a short tour with a 640×480 camera, records it, and exports it in the nerfstudio layout (for NeRF and Gaussian splatting) and the TUM layout (for SLAM). The camera poses are simulator ground truth, so there is no COLMAP step.

python3 record_and_export.py
recorded 251 frames from camera 'front'
nerfstudio: runs/flight/nerfstudio
TUM:        runs/flight/tum

It takes about 4 seconds and writes 36 MB under runs/flight. Training on the result is the heavy step and is not part of this tutorial: ns-train splatfacto --data runs/flight/nerfstudio needs nerfstudio and a CUDA GPU. For a smaller dataset lower width, height or fps in the script.

Each step runs in a fixed order: links in (may block, for lockstep) → controllers that are due → physics → renderer → links out → callbacks.

Conventions

World frame ENU (x east, y north, z up), body frame FLU (x forward, y left, z up), quaternions (w, x, y, z), SI units. MAVLink's NED / FRD is converted inside the MAVLink link and nowhere else.

Three levels of control

1. Config only

roboforge: 1
name: quad
robot: quadrotor
physics: {type: mujoco}
renderer: {type: mujoco, fps: 10}
links:
  - {type: mavlink, mode: vehicle}
controllers:
  - {type: multirotor, rate: 250}
callbacks:
  - {type: viewer}

Every key under a part is an argument of that class. There is no inheritance between configs and no interpolation: what you read is what is built. Override from the command line with path=value: python3 -m roboforge run app.yaml physics.substeps=2 links.0.url=udpout:10.0.0.2:14550. Unknown keys are an error.

2. Your own classes

# controller.py, next to app.yaml
import numpy as np
import roboforge as rf

class Patrol(rf.Controller):
    def step(self, obs, t):
        corner = [(0, 0, 1.5), (2, 0, 1.5), (2, 2, 2.0), (0, 2, 1.5)][int(t / 4) % 4]
        return rf.Setpoint(position=np.array(corner, float))
controllers:
  - {type: "controller:Patrol", rate: 0.25}     # module:Class, looked up next to the config
  - {type: multirotor, rate: 250}

step may return nothing, one message (published on that message's standard signal), a list, or {signal: message}. A plain function works too: @rf.controller(rate=50).

3. Everything exposed

app = rf.App.from_config("app.yaml", controllers=[MyController()])   # replace a whole part
app.setup()
model, data = app.physics.raw          # mujoco.MjModel, mujoco.MjData
node = app.links[0].raw                # the rclpy node (Ros2Link) or pymavlink connections (MavlinkLink)
while app.time < 10:
    app.step()                         # your loop
    if data.ncon > 12: break
app.close()

Your own backend or transport is a class with the same few methods as roboforge.component.Physics / Renderer / Link, used as type: "mypkg.mysim:MySim" or registered by name with rf.PHYSICS.register("mysim", MySim). A replacement simulator is indistinguishable to the rest of the stack, because ROS and MAVLink compatibility lives in the links, not in the simulator.

Controllers: from a PID loop to a learned policy

The contract is one method, so the simple case stays simple:

pid = rf.PID(kp=40, ki=15, kd=5)

def hold_elbow(obs, t):
    js = obs.joint
    u = np.zeros(3)
    u[2] = pid(-1.0 - js.position[2], 0.002, rate=-js.velocity[2])
    return rf.ActuatorCommand(values=u)

rf.App(robot="arm", controller=hold_elbow).run()

Larger systems are several controllers side by side, each at its own rate, talking through the bus. A hierarchy is nothing more than that: a slow layer publishes cmd/setpoint or cmd/joint, a fast layer turns it into motor commands.

NeedHow
Different ratesrate on each controller (Hz). Omit it to run every physics step.
A slow model must not stall the looprf.Async(policy, rate=50, timeout=1.0, fallback=...) runs it in a worker thread on a frozen copy of the observations
Action chunksReturn rf.Chunk(actions=[...], dt=0.1); the actions are played out on time
The model is late or crashesfallback: a message, a function, or "hold", used after timeout seconds without a result
Images, languageobs.camera("front"), obs.instruction
Trainingapp.as_env(reward=..., terminated=...) gives a Gymnasium environment over any stack

examples/pid_to_policy.py shows a 2 Hz stand-in for a large model, with 300 ms inference and action chunks, above a 500 Hz PID loop that never slows down. Replacing the stand-in with a real VLA or world-model planner changes that one class.

MAVLink link

ModeThe app isDetails
vehiclethe vehicleSends HEARTBEAT, ATTITUDE, LOCAL_POSITION_NED, GLOBAL_POSITION_INT, GPS_RAW_INT, SYS_STATUS, EXTENDED_SYS_STATE, HOME_POSITION. Handles arm / disarm, takeoff, land and SET_POSITION_TARGET_LOCAL_NED (position or velocity, with yaw). Refuses takeoff while disarmed and disarm while flying. Default endpoints: UDP 14550 (ground station) and 14540 (API).
clienta MAVLink clientTelemetry becomes state/pose, state/twist, state/status; cmd/setpoint is streamed as position targets; link.arm(), takeoff(alt), land() return whether the autopilot accepted. With PX4 on the other end it asks for OFFBOARD mode once targets are flowing and converts the takeoff height to PX4's above-sea-level convention.
hilPX4 SITL's simulatorListens on TCP 4560; sends HIL_SENSOR (IMU, magnetometer, barometer) and HIL_GPS; in lockstep: after PX4's first motor command, the simulator advances only when PX4 has answered the last sample with HIL_ACTUATOR_CONTROLS. Samples go out at sensor_rate (250 Hz) with a little noise (sensor_noise), because PX4 rejects readings that never change. PX4's motor order is matched to the model's rotor layout automatically for an X quadrotor; motor_map overrides it. If PX4 exits, the app stops with an error.

Flying a real PX4 in the simulator

PX4 runs as its own program and uses the app as its simulator. Build PX4 SITL once (about ten minutes; Gazebo is not needed):

cmake -S ~/PX4-Autopilot -B ~/px4-build -G Ninja -DCONFIG=px4_sitl_default
ninja -C ~/px4-build px4

Create a project with Autopilot link: PX4 in the loop (or use tests/px4/app.yaml), start the app, then start PX4 with its "no simulator" airframe from an empty working folder:

python3 -m roboforge run app.yaml --headless                      # terminal 1: waits for PX4 on TCP 4560
mkdir -p ~/px4-run && cd ~/px4-run                                # terminal 2
PX4_SYS_AUTOSTART=10016 PX4_SIM_MODEL=none_iris ~/px4-build/bin/px4 -d ~/px4-build/etc -w . -s etc/init.d-posix/rcS

PX4 prints Ready for takeoff! after a few seconds of sensor data. Anything that flies PX4 now flies the MuJoCo vehicle on UDP 14540: the mission script from tutorial 3 works unchanged (python3 mission.py), as does a plain pymavlink or MAVSDK program. tests/px4/run.sh and tests/px4/client.sh do all of this in one command each.

A PX4 binary built on another machine or in a container may not start here (GLIBC_2.4x not found). Build it on the machine that runs it. Build into a separate folder, as above, to leave an existing build/ alone.

Rendering and datasets

A renderer is separate from the physics. It has one required method, render(camera) → Image, and a list of passes that run on every frame:

renderer = rf.MujocoRenderer(width=640, height=480, fps=10)

@renderer.add_pass
def night(image, renderer):
    image.data = (image.data * 0.3).astype("uint8")     # any post-process, extra buffer, or a different picture entirely
    return image

The recorder callback saves a run as a dataset, with simulator ground-truth poses for every frame:

ds = rf.Dataset("runs/flight")
ds.export_nerfstudio("out/ns")      # transforms.json + images:  ns-train splatfacto --data out/ns
ds.export_tum("out/tum")            # rgb.txt + groundtruth.txt, for SLAM systems and trajectory evaluation

or python3 -m roboforge data export runs/flight --format nerfstudio --out out/ns. examples/record_and_export.py flies a tour and exports both.

Your own robot

robot: {urdf: ~/robots/humanoid.urdf, profile: articulated}      # or {mjcf: model.xml, profile: arm, base: torso}

profile is articulated (any jointed robot, including humanoids), arm, multirotor or diffdrive. Joints, actuators and an IMU are read from the model; for a multirotor the mapping from motors to thrust and torques is computed from the rotor sites, so the built-in controller flies any rotor layout. URDF mesh paths must resolve from the URDF's folder.

Python environment

The SDK ships inside the IDE and is unpacked to ~/.roboforge/sdk/python; projects that use it get it on PYTHONPATH. Its optional parts need packages:

PartNeeds
MuJoCo physics and renderermujoco
MAVLink linkpymavlink

Gymnasium adaptergymnasium

Two ways to get them:

  • Set up SDK environment (Stack view): creates ~/.roboforge/envs/sdk-venv, a virtualenv on the system Python (so a system ROS 2 stays importable) with those packages, and sets it as the project's Python. No sudo; uses uv if installed, otherwise python3 -m venv.
  • Sync SDKs: installs the project's full isolated environment, with the SDK, MuJoCo and pymavlink as components.

Debugging an app

Three tools cover most problems. The method: run, read what it says, fix one thing, run again.

CommandTells you
python3 -m roboforge info app.yamlWhat is in the app: parts, rates, and who publishes each signal. Opens no ports.
python3 -m roboforge run app.yaml --checkThe usual reasons a robot does not do what was expected, while it runs: nothing drives the motors, actuators stuck at their limits (often targets in degrees), a disarmed vehicle, the loop too slow, free fall, dropped messages.
python3 -m roboforge run app.yaml --tapEvery signal once a second: its rate, its publisher, its latest value. A missing row means nothing publishes it.

Mistakes in an app file stop it before the first step with one line that names the problem, lists what is allowed and suggests the nearest match, for example unknown config keys: controlers. Did you mean 'controllers'?. Bad input from ROS or MAVLink (nan, a wrong-sized command) is dropped with a warning and never reaches the robot.

examples/debugging/ has a deliberately broken app to practise on (broken_arm, five mistakes), and scripts to step through a run, compare two recordings, sniff a MAVLink port and measure this machine's speed.

Four tutorials build parts of your own and show how little each takes: a neural-network policy trained and deployed with rf.Policy (also with PyTorch and stable-baselines3 PPO), a Gaussian-splat renderer in numpy (render() is the only method), a physics solver checked against MuJoCo, and sensors plus EKF-SLAM scored with rf.eval (ATE, RPE, TUM files). See examples/custom_* and tutorials 14 to 17.

A URDF of your own gets a torque motor per joint and a ground plane added; floating_base: true frees its base for humanoids and legged robots (examples/custom_urdf).
