RoboForge guide

Open a robotics workspace, let the IDE work out what it can launch, and start the whole stack (world, SLAM, viewers, teleop) from one dialog.

Build and start

cargo build --release --features desktop   # native window (Tauri)
cargo build --release                      # browser-only build

./target/release/roboforge                 # desktop build: opens the window
./target/release/roboforge --browser       # open a browser tab instead
./target/release/roboforge --port 7890     # if 7878 is taken

The desktop build needs the WebKitGTK development packages once:

sudo apt install libwebkit2gtk-4.1-dev build-essential libxdo-dev libssl-dev libayatana-appindicator3-dev librsvg2-dev

Closing the window (or Ctrl+C) stops every job and terminal the IDE started, so simulators do not outlive it.

Several instances. You can run more than one RoboForge at a time, for example one per project. The first uses port 7878; if that is taken, the next one picks a free port by itself and says which. Each instance has its own jobs, terminals and embedded VS Code server. Pass --port N only if you need a fixed port; a fixed port that is busy is an error.

Example: a TurtleBot3 simulation workspace

The example is a plain colcon workspace, ~/turtlebot3_ws, holding a checkout of turtlebot3_simulations (packages turtlebot3_gazebo and turtlebot3_fake_node). Cartographer, Nav2 and teleop are not in the workspace; they are the installed packages turtlebot3_cartographer, turtlebot3_navigation2 and turtlebot3_teleop. Launching this by hand takes four terminals, an exported variable and the right arguments:

export TURTLEBOT3_MODEL=burger
ros2 launch turtlebot3_gazebo turtlebot3_world.launch.py                      # terminal 1
ros2 launch turtlebot3_cartographer cartographer.launch.py use_sim_time:=True # terminal 2
ros2 run turtlebot3_teleop teleop_keyboard                                    # terminal 3
ros2 run nav2_map_server map_saver_cli -f ~/map                               # terminal 4

RoboForge derives all of that from the directory tree.

1. Open the workspace

  1. Click Open, type ~/turtlebot3_ws in Folder.
  2. Under Or set up an existing ROS workspace in place, pick the ROS distro (Jazzy) and click Set up this workspace. Only roboforge.json and .roboforge/ are added; packages, build/ and install/ are untouched. Next time, just open the folder.
  3. If the workspace has never been built, run Build workspace (colcon) from the Run menu.

When the project loads, the tree is scanned and a notice reports what was found:

Detected in this project: 8 simulation worlds, 1 SLAM launch, 1 navigation launch, 1 teleop, 2 bringup launches.
Created the launch configuration "World + SLAM + teleop": pick it in the Run menu, or open Launch to edit it.
TURTLEBOT3_MODEL still needs a value (Launch dialog).

That first launch configuration is written to roboforge.json once. It is selected in the Run menu, so after choosing the robot model (next step) ▶ Run starts the whole stack.

  • Environment. The launch files read TURTLEBOT3_MODEL without a default, so it is listed as required. The choices come from the URDF files in the packages. Your pick is saved in the project's roboforge.json (env) and exported for every job and terminal. Rows that depend on an unset variable are disabled until it is set.
  • One row per role. Each drop-down lists every launch file of that role; the best default is preselected (turtlebot3_world rather than empty_world or the DQN stages). Launch files that are only included by others (spawn_turtlebot3, robot_state_publisher, occupancy_grid) are listed last as “↳ included”.

  • Launch starts one entry on its own. Jobs get a tab in the bottom panel (■ stops them); pressing Launch again on a running entry just shows its tab.

3. Launch the stack

▶ Run with “World + SLAM + teleop” selected in the Run menu does this in one click. ▶ Launch stack in the dialog does the same for whichever rows are ticked, in this order:

4. Map, then navigate

  1. Drive the robot around with the teleop terminal until the map in RViz looks complete.
  2. In Launch, choose Navigation ▸ save map. It writes maps/map.yaml and maps/map.pgm into the project.
  3. Stop the SLAM job, then launch Navigation ▸ navigation2. Once maps/map.yaml exists, map:=…/maps/map.yaml is added to the command automatically.

Projects on the RoboForge SDK

The RoboForge SDK is a Python library, shipped with the IDE, in which the simulator, ROS 2 and MAVLink are interchangeable parts. The IDE creates, understands and launches projects built on it.

WhereWhat
New ▸ Build on the RoboForge SDKThe stack picker: Simulator (MuJoCo or none) × Robot (quadrotor, arm, wheeled base, or your own URDF / MJCF) × Autopilot link (MAVLink vehicle, PX4 in the loop, MAVLink client) × ROS 2. Quick picks cover MuJoCo + ROS 2, MuJoCo + MAVLink, ROS 2 + MAVLink and all three. It creates app/app.yaml, a starter controller or mission script, run configurations and a launch configuration.
Stack (header)What the app is made of: robot, physics, renderer, controllers with their rates, each link with the signals it takes from and puts on the bus, and every signal with its source.
Stack ▸ Set up SDK environmentCreates a small Python environment with MuJoCo and pymavlink on top of the system Python, without sudo, and points the project at it.
Launch, Run menu, VS Code tasksAn app.yaml is recognised as “App: <name>”, its MuJoCo models get a viewer entry, and a mission script next to it is chained after the app in the suggested launch configuration.
SDK ManagerThe SDK and pymavlink are components like any other.

Importing any project

Open ▸ Import… brings in a folder that is not a RoboForge project, in the way Android Studio imports a project: it inspects the folder, shows what it found and what it will create, and only then creates the project. Nothing is written into the folder you import. RoboForge's own files (roboforge.json, .roboforge/) go to ~/roboforge-projects/<name>/, and the imported folder is attached to that project as a workspace. Importing the same folder again just reopens the project.

It works for ROS workspaces and for projects with no ROS at all. Example: ~/pythonProjects/8ol, a PX4 + Gazebo project made of Python scripts, a run.sh with subcommands, SDF worlds, a pytest suite and Sphinx docs. The import summary for it reads:

For a ROS workspace the rules under How projects are understood apply in addition.

Launch configurations

A launch configuration is a named, ordered list of commands saved in the project. It is the editable counterpart of the detected list: RoboForge creates the first one for you, and you can change it or write your own.

WhereWhat you can do
Run menu (header)Launch configurations are listed first (🚀). Pick one and press ▶ Run.
Launch dialog, top section▶ Run, Edit or delete each configuration; ＋ New configuration; Create from detection adds the suggested stack again.
Launch dialog, footerSave ticked as configuration turns the rows you ticked in the detected list into a configuration and opens it in the editor. ■ Stop all stops every running job.

The editor

Each step has a name (the tab title), a command, the folder it runs in (project or one of its workspaces), whether it runs as a job or in a terminal, when it starts (right away, or after previous: only once the step before it has finished, and only if that step succeeded), and an optional wait in seconds before it starts. Steps can be reordered with ↑ ↓. ＋ Add command adds an empty step; Add detected… inserts any launch the scan found.

A command is any shell line and runs inside the project environment: ros2 launch …, ros2 run …, ./scripts/start_robot.sh, ros2 bag record -a, or several commands joined with &&. Use terminal for anything that reads the keyboard, and wait to give a simulator time to come up.

This is what the generated TurtleBot3 configuration looks like in roboforge.json, with one custom step added by hand:

"launch": [
  {
    "name": "World + SLAM + teleop",
    "steps": [
      { "name": "World: turtlebot3_world", "cmd": "ros2 launch turtlebot3_gazebo turtlebot3_world.launch.py", "workspace": "ros2" },
      { "name": "SLAM: cartographer", "cmd": "ros2 launch turtlebot3_cartographer cartographer.launch.py use_sim_time:=True", "workspace": "ros2", "wait": 7 },
      { "name": "Record bag", "cmd": "ros2 bag record -o bags/run1 /scan /odom /tf" },
      { "name": "Control: teleop_keyboard", "cmd": "ros2 run turtlebot3_teleop teleop_keyboard", "terminal": true }
    ]
  }
]

A step whose job is already running is skipped, so running a configuration twice does not start a second simulator.

Environment and setup scripts

The Environment button in the header controls how the project environment is put together. It applies to everything that runs in the project: builds, run and launch configurations, and terminals. Paths can be absolute, start with ~/, or be relative to the project folder.

FieldEffect
ROS setup scriptSourced instead of the project SDK environment. Use it for a system install (/opt/ros/jazzy/setup.bash) or a ROS you built from source.
Also sourceOne script per line, sourced in order after ROS and the project's workspace overlays: underlay workspaces, vendor SDK setup files, your own scripts.
PATH additionsOne folder per line, put in front of PATH.
PYTHONPATH additionsOne folder per line, put in front of PYTHONPATH.
Python for buildsThe interpreter colcon (COLCON_PYTHON_EXECUTABLE), CMake's FindPython3 (Python3_ROOT_DIR) and python3 on PATH should use, for example a virtualenv's bin/python.
VariablesNAME=value, one per line, exported last so they win: ROS_DOMAIN_ID, RMW_IMPLEMENTATION, TURTLEBOT3_MODEL, RF_JOBS…
bash and zsh scripts. Activation runs in bash. If you list a .zsh file that has a .bash sibling (ROS ships setup.bash next to setup.zsh), the .bash one is sourced. A zsh-only script is sourced as is, which works when it sticks to plain export lines and fails on zsh-only syntax. A script that does not exist prints one warning line and the rest of the environment still loads.

Save and check saves, then runs a short job that prints which ROS distro, ros2, colcon and python3 the environment resolves to, and the first entries of PATH, PYTHONPATH and AMENT_PREFIX_PATH, so you can see the effect of a change straight away.

The same settings in roboforge.json:

"setup": {
  "ros_setup": "/opt/ros/jazzy/setup.bash",
  "source": ["~/underlay_ws/install/setup.bash", "scripts/robot_env.sh"],
  "path": ["~/tools/bin"],
  "pythonpath": ["python"],
  "python": "~/venvs/ros/bin/python"
},
"env": { "TURTLEBOT3_MODEL": "burger", "ROS_DOMAIN_ID": "7", "RF_JOBS": "4" }

Order of activation: ROS (your setup script, else the SDK environment, else /opt/ros/<distro>) → workspace overlays → “also source” scripts → PATH and PYTHONPATH additions → build Python → variables.

How projects are understood

Nothing above is specific to TurtleBot3. Each time a project is opened (and each time the Launch dialog opens) RoboForge walks the tree and applies these rules:

What it looks atWhat it concludes
Every package.xml under the ROS workspaces (build/, install/, log/, .git are skipped)The workspace packages, and whether each one is built (install/<pkg>). Unbuilt packages are shown but disabled with “run the workspace build first”.
launch/ in each package: *.launch.py, *.launch.xml, *.launch.yaml, *.launchOne entry per file: ros2 launch <pkg> <file> (roslaunch for ROS 1).
The first word of the package names (turtlebot3_gazebo)The package family. Installed packages of the same family in the environment (turtlebot3_cartographer, turtlebot3_navigation2, turtlebot3_teleop, turtlebot3_bringup) are scanned the same way and marked “environment”.
File and package names, and the launch file's contentThe role: SLAM (cartographer, slam, rtabmap, mapping…), navigation (nav2, navigation, amcl, localization), control (teleop, joy, keyboard), visualization (rviz, rqt, foxglove), manipulation (moveit), simulation (the file starts Gazebo, Webots, Isaac or MuJoCo, or is named world/gazebo/sim), otherwise bringup or other.
Launch files named inside other launch files of the same packageHelpers (“↳ included”), never chosen as a default.
os.environ['NAME'] in launch files, followed through includesRequired variables. <FAMILY>_MODEL gets choices from the packages' URDF file names.
use_sim_time declared in a launch file, and a simulator present in the projectuse_sim_time:=True is appended.
Executables with “teleop” in their name in the family packages; otherwise teleop_twist_keyboard if installedKeyboard control entries that open in a terminal.
*.rviz files, *.world and worlds/*.sdfRViz starts with the project's config; a project with a world but no launch file gets a plain gz sim -r <world> entry.
The executables on the project environment's PATHEntries whose tools are missing are disabled and show the install command.

The scan reads files only; nothing is executed and nothing is written to the workspace. For the TurtleBot3 workspace it takes about half a second.

VS Code inside RoboForge

The ◧ VS Code button in the header replaces the built-in editor with a full Visual Studio Code, embedded in the same window. It is your own installed VS Code running its local web server (code serve-web), so you get the normal extension marketplace: IntelliSense and language servers (Python, C/C++, Rust…), and chat or agent extensions such as GitHub Copilot or Claude Code. The RoboForge header (Run, Launch, Environment) and the bottom panel stay where they are.

TopicBehaviour
RequirementVS Code installed with the code command on PATH. The first start downloads the matching server (about a minute); later starts take a few seconds.
What opensA generated workspace, .roboforge/project.code-workspace: the project folder, plus every project workspace that lives somewhere else (for example an external ~/turtlebot3_ws) as additional roots.
EnvironmentThe server is started inside the project environment, so tasks, debuggers and language servers see ROS, the workspace overlays and your setup scripts. The workspace also defines a RoboForge terminal profile (bash with the project environment) and makes it the default.
Launch and run from inside VS CodeThe workspace carries a VS Code task for everything RoboForge can start. Terminal ▸ Run Task… (or F1 → “Tasks: Run Task”) lists them:
  • 🚀 <name>: each launch configuration. Its steps start side by side in split terminals, honouring the waits; terminal steps get the keyboard focus.
  • RoboForge: <name>: each run configuration. The build is the default build task, so Ctrl+Shift+B builds the workspace; “Tasks: Run Test Task” runs the tests.
  • Detected ▸ <name>: every launch the scan found (worlds, SLAM, navigation, teleop, RViz…).
Stop them with “Tasks: Terminate Task”. Every task sources the project environment itself, so it does not depend on your login shell.
Kept in syncThe tasks are regenerated whenever you change launch configurations, run configurations, the environment or roboforge.json in RoboForge; VS Code picks the change up without a reload. The file is generated, so put personal settings in VS Code's user settings or a folder's .vscode/.
IntelliSenseThe workspace sets Python extra paths from the environment's PYTHONPATH, C/C++ include paths from the ROS and workspace prefixes, the build Python if you chose one, compile_commands.json when the workspace has one, and XML/YAML highlighting for .launch, .urdf, .xacro, .sdf, .world and .rviz files.
RoboForge dialogsThe RoboForge header stays above VS Code, so Launch (editing configurations, detection), Environment, Workspaces, Modules, Sync SDKs and the SDK Manager are one click away while you edit in VS Code.
AppearanceThe embedded VS Code is recoloured to match RoboForge: the same backgrounds, borders, orange accent, syntax colours and monospace font, in both light and dark. Like RoboForge it follows the system light/dark setting. The colours are applied to whichever light or dark theme is active, so choosing a different VS Code theme keeps the RoboForge palette on top; to opt out, override workbench.colorCustomizations in your VS Code user settings.
Remembered stateEach project's VS Code runs on the same local port every time, so VS Code remembers that you trusted the workspace, your layout and your sign-ins between sessions.
Restricted ModeVS Code opens a new folder in Restricted Mode. Trust the workspace (status bar, or the prompt the first time you run a task) to enable tasks, the terminal profile and all extensions.
ExtensionsInstall them from the Extensions view inside the embedded VS Code. They are kept in ~/.vscode-server, separate from the desktop VS Code's extensions, so sign-ins (Copilot and others) are done once here.
Switching back◧ Built-in editor returns to the RoboForge editor; VS Code keeps running and reappears instantly.
StoppingThe server is the job “VS Code server” in the bottom panel; ■ stops it. Closing RoboForge stops it too.
AccessThe server listens on 127.0.0.1 only, on a random port, and requires a random token that is kept in a private file (~/.roboforge/run/vscode-token-<port>).

Terminals

＋ Terminal in the bottom panel (or Ctrl+`) opens an interactive bash on a real pty, with your ~/.bashrc and then the project environment loaded, so ros2, colcon and the workspace overlay are ready. Several terminals can be open next to the job tabs. Copy with Ctrl+Shift+C, paste with Ctrl+Shift+V. The ⌃ button makes the panel taller.

Environment and builds

TopicBehaviour
ROS environmentThe project's RoboStack environment under ~/.roboforge/envs is used when it has been synced. If it has not, and /opt/ros/<distro> exists, the system install is sourced instead and a one-line note says so.
Workspace overlayinstall/setup.bash (or devel/setup.bash) of every ROS workspace in the project is sourced after ROS.
Project variablesEverything under env in roboforge.json is exported for jobs and terminals.
Rust and user tools~/.cargo/env and ~/.local/bin are loaded, so cargo is found even when the IDE was started from a launcher.
Build parallelismBuilds started from the IDE leave two cores free: RF_JOBS defaults to cores − 2 and sets MAKEFLAGS=-j$RF_JOBS -l$RF_JOBS, CMAKE_BUILD_PARALLEL_LEVEL and CARGO_BUILD_JOBS unless you already exported them. To change it, add for example "RF_JOBS": "4" to env in roboforge.json.

Troubleshooting

SymptomCause and fix
“SDK environment … is not installed yet” and ros2: command not foundNeither the project environment nor /opt/ros/<distro> exists. Run Sync SDKs, or install that distro system-wide.
A Launch row is disabled with “Set TURTLEBOT3_MODEL above first”Pick a value in the environment section at the top of the dialog.
A row says the package is not builtRun Build workspace (colcon), then reopen Launch.
Gazebo row disabled: “gz is not in this environment”sudo apt install ros-<distro>-ros-gz, or run Sync SDKs with the Gazebo module.
“No display is available”RoboForge was started without DISPLAY / WAYLAND_DISPLAY (for example over plain SSH). Start it from a desktop session.
UserWarning: Unbuilt egg for pytest-repeat during colcon buildsHarmless warning from the system setuptools. Hide it with "PYTHONWARNINGS": "ignore::UserWarning" in the project's env.
cargo: command not found in your own zshA line in ~/.zshrc that overwrites PATH drops ~/.cargo/bin. Add . "$HOME/.cargo/env" after it.
